# slicer — 형상 적응형 원뿔(conical) 슬라이싱 알고리즘

STL 모델을 분석해 부위별로 원뿔 슬라이싱 각도/방향을 **자동으로, 가볍고
투명하게** 결정하는 알고리즘 (고등학교 R&E). 무거운 연구용 최적화 슬라이서와
단순 고정각 원뿔 슬라이서(RotBot 등) 사이의 빈 자리를 노린다.

> "연구실의 성능을 메이커의 손에."

## 설치

```
pip install -r requirements.txt
```

자동 생성 모델에 대한 원뿔각 반복 검증은
[`docs/random_validation_pipeline.md`](docs/random_validation_pipeline.md)를 참고한다.
`python tools/run_random_validation.py --count 100 --seed 20261002 --output-dir results/random_validation`
명령으로 내부 기준선을 실행할 수 있다. 외부 검증기는 별도 설치해야 하며,
REP5X 충돌과 물리 출력 가능성의 독립 검증은 아직 완료되지 않았다.

## 실행

```
python3 overhang_analysis.py [model.stl]        # Stage 1: 오버행 분석 (면 법선)
python3 angle_sweep.py                           # Stage 2: 각도별 남은 서포트 곡선 -> angle_sweep.png
python3 cone_selector.py [model.stl]             # Stage 3: 각도/방향 자동 결정 + 이유
python3 region_selector.py [model.stl]           # Stage 4: 부위별(오버행 심한 정도) 각도 결정
python3 compare_overhang_methods.py [model.stl]  # 검증: 면법선 vs 레이어별 2D 판정 비교
python3 compare_complexity.py [model.stl]        # 핵심: '복잡도 vs 성능' 균일/구간별/세밀 비교
python3 analyze_k.py [model.stl]                  # 구간별 이득이 k에 어떻게 의존하나 -> analyze_k.png
python3 compare_ceiling.py [model.stl]            # 실현 가능한 밴드 계획 vs 이상적 천장
```

STL 경로를 안 주면 데모용 구(sphere)로 실행된다.

### 슬라이싱 파이프라인 (STL → 원뿔 G-code)

```
python3 conical_slice.py model.stl                       # 각도 자동 (J 기준, --k 로 조정)
python3 conical_slice.py model.stl --angle 30 --direction outward   # 수동 지정
python3 conical_slice.py model.stl --profile "0:15,10:15,14:35,30:35"  # 가변각 θ(Z′) 수동
python3 conical_slice.py model.stl --auto-bands 2        # 밴드 자동 탐색 → 가변각 프로필
python3 conical_slice.py model.stl --mode open5x         # Open5x 5축 기계좌표 [실험적]
python3 conical_slice.py model.stl --machine-profile profiles/machine.example.ini
python3 conical_slice.py model.stl \
  --slicer-cmd "prusa-slicer -g --load profiles/conical_pipeline.ini --dont-arrange -o {gcode} {stl}"
```

### ⚠ 실물로 뽑으려면 기계 프로파일이 필요하다

`--machine-profile` 없이 나온 G-code 에는 **예열·호밍·프라임·냉각이 없다.**
이 저장소의 내장 슬라이서는 연구용이라 `G21/G90/M82` 와 경로만 내보낸다 —
그 파일을 그대로 프린터에 넣으면 안 된다. 기계 설정은 경로 생성과 성질이 다르므로
INI 파일로 분리했다(`conical/machine.py`).

```ini
[machine]
name = Open5x (Prusa 개조)
bed_temp = 60
start_gcode =
    M140 S{bed_temp}
    G28
end_gcode =
    M84
```

치환은 `{key}` 하나뿐이다 — 프로파일 자신의 키와 슬라이싱이 정한
`{layer_height} {angle} {direction} {mode} {source_stl}`. 채울 값이 없으면
조용히 비우지 않고 **멈춘다**(기계로 나가는 파일이므로).

`profiles/machine.example.ini` 는 **템플릿이고 우리 기계에서 확인된 값이 아니다.**
온도·호밍·프라임 좌표를 반드시 확인하고, 5축 U/V 호밍은 제원을 받기 전까지
비워 뒀다(TODO 표시).

가변각 프로필은 tanθ 를 Z′에 조각별 선형으로 보간하고(가역성 조건
`c·r_max·s < 1`, 블렌드 최소 폭 `w_min = c·r_max·Δtanθ` 자동 검증),
상수 프로필은 기존 고정각과 수치적으로 동일하다(회귀 테스트로 강제).

블렌드에는 **층간격 제약**도 걸린다: 변환공간에서 층고 간격으로 자른 레이어가
실공간에서 `m = 1 − c·r·s` 배로 벌어지므로, 배율을 `MAX_SPACING_FACTOR`
(기본 1.5) 이내로 두는 최소 폭 `w ≥ r_b·|Δtanθ|/(limit−1)` 을 강제한다.
반경 `r_b` 는 **그 높이의 최대 반경**이라(`meshio.RadiusProfile`) 경계를 반경이
작은 높이로 옮기면 블렌드가 싸진다 — 자동으로 그렇게 옮긴다(`--spacing-limit 0`
으로 끄면 옛 동작). 이 제약은 툴패스 검사기가 실측으로 잡아낸 결함에서 나왔다.

### 하드웨어 플랫폼 비교 (REP5X vs 뱀부랩 개조)

`analyze_sync.py` 는 기계가 없어도 G-code 만으로 **회전축에 무엇이 요구되는지**를
잰다. 자세한 것은 [`docs/platform_comparison.md`](docs/platform_comparison.md).

세 줄 요약:

1. **요구 각속도가 축 근처에서 발산한다** — `ω = f/r`. 최대 7,396(funnel) /
   18,211(lamp) deg/s. 그래서 슬라이서나 펌웨어가 피드를 깎아야 하고,
   **축의 최대 각속도가 출력 시간을 정한다** (720 deg/s 확보 시 손해 10% 안쪽).
2. **동기 오차는 `f·Δt`** — 반경이 약분된다. 1ms 지각이면 최대 46µm(압출폭의 10%),
   10ms 면 466µm 로 **압출폭을 넘는다.** 외부 컨트롤러는 1ms 이내 동기가 필요하다.
3. **기계 XY 가 X축 직선으로 축퇴한다** (기계 Y 폭 = 0.0000mm). `V = −φ(p)` 라
   압출점이 항상 방위각 0 에 오기 때문이다. → **기반 프린터의 XY 속도는 이 모드에서
   거의 쓰이지 않는다.** 병목은 회전축이다.
   ⚠ **베드 회전식에 한정된 결론이다.** REP5X 는 헤드 회전식으로 확인됐고
   (2026-09-19, [`docs/build_cost.md`](docs/build_cost.md) ⓪), 거기서는 헤드가
   부품 XY 를 전부 훑어 축퇴가 없다 (funnel 26.62 × **26.62**).

⚠ 기구학 요구량이지 실제 시간이 아니다(가속도·저크 무시 → 하한). 축 토크·관성은
보지 않는다.

`analyze_motion.py` 가 그 하한에 **축별 가속도·저크를 넣는다** (사다리꼴 운동 계획,
`conical/motion.py`). 여기서 나온 것:

4. **출력 시간과 배선 되감기 시간은 갈라서 봐야 한다** — lamp 24° 는 출력 13.6분에
   되감기가 **75.4분**이었다. 합계 89분만 보면 모델이 깨진 줄 안다. 되감기는
   재료를 놓지 않는 부대비용이고 **무제한 회전축이면 0** 이라, 섞으면 기계 비교가
   망가진다 (`plan_motion` 이 `print_seconds` 를 따로 돌려준다).
5. **되감기 시간 ≒ 되돌린 각도 ÷ 되감기 속도** — 감긴 만큼은 반드시 되돌려야 해서
   총 각도가 고정된다. 허용 회전을 2 → 8 로 늘려도 80.2 → 79.6분뿐이다.
   → **되감기 문턱은 시간이 아니라 배선 여유로 정할 것.** 시간은 `--v-rewind-feed`
   로 줄인다.
6. **XY 스펙은 출력 시간을 전혀 안 준다** — 속도·가속도를 4배로 올려도 1.00×.
   위 3번의 XY 축퇴를 시간 축에서 독립적으로 확인한 것이다. 움직이는 스펙은
   회전축뿐이고, **가속도가 최대 속도보다 더 먹는다** (2× 에서 0.88 vs 0.96) —
   구간이 짧아 정속에 도달하지 못하기 때문이다. 가속을 넣으면 출력 시간이 하한의
   1.8~2.1배가 된다.

⚠⚠ 축 한계값은 **전부 가정값**이다(회전축은 특히 근거가 없다). 펌웨어 플래너의
근사이기도 하다 — 입력 셰이핑·S커브·세그먼트 합치기가 빠져 있다. **절대 시간이
아니라 프로파일 간 비교로 쓸 것.**

`analyze_envelope.py` 는 **최대 각도를 무엇이 정하는가**를 본다
(`conical/envelope.py`).

7. **3축에서 각도를 막던 노즐 간섭이 5축에서는 정의상 불가능해진다** — 원뿔
   레이어 `z = z₀ − r·tanθ` 를 기계좌표에 넣으면 `r` 이 약분돼
   `z_m = cosθ(z₀+d) − d` 가 된다. **레이어 하나 = 기계 Z 값 하나**이고 단조증가라,
   기계공간에서 그냥 **평면 적층**(층고 `h·cosθ`)이다. 실제 G-code 에서 층 내부
   편차 1e-14, 기계 Z 단조 확인. funnel 의 3축 MAX_ANGLE 은 24° 였다.
8. **⚠⚠ 지금 G-code 를 그대로 걸면 어떤 각도도 안 된다** — 틸트하면 베드면이
   기계 Z 로 `−d(1−cosθ)` 만큼 내려간다(20° 에서 −3.02mm). 소프트리밋이 0 이면
   θ>0 이 전부 잘린다. **Z 영점을 제작 전에 정해야 한다.**
9. **대각선 규칙** — 틸트는 부품 경계상자를 θ 만큼 회전시킨다. 그래서
   **0~90° 전 구간을 쓰려면 X·Z 이동이 둘 다 `√(R²+H²)` 이상**이어야 한다
   (70개 조합 불일치 0건). 피벗 깊이 d 는 스팬에서 **약분되고**, 대신 회전 베드를
   X 중앙에서 `sinθ·d` 만큼 옮겨 달아야 한다는 **장착 위치**를 정한다.

⚠ 엔벨로프 값도 가정이다. 그리고 여기 나온 각도는 '기계가 못 하는 곳'의 상한이지
**써야 할 각도가 아니다** — 서포트 감소·층간격·표면 품질은 별개 질문이다.

⚠⚠ **7~9 는 베드 틸트식(Open5x)에만 해당한다.** REP5X 는 헤드 회전식이라 부품이
고정이고, 원뿔 레이어가 기계공간에서 수평이 되지 않는다 — **노즐 간섭이
되살아나고 도달 영역 계산을 다시 해야 한다.**

### 구축 비용·제작 난이도 (R6)

[`docs/build_cost.md`](docs/build_cost.md) — 조사로 답하는 항목.

10. **REP5X 는 헤드 회전식이다** (조립 지침 원문으로 확정). 두 회전축이 X 캐리지
    위에 얹히고 슬립링이 핫엔드 배선을 나른다. **베드는 손대지 않는다.**
    → 위 3·7·8·9 의 적용 범위가 갈린다
11. **비용으로는 안 갈린다** — REP5X 는 프로젝트 공식 **~$150** + 12~19시간,
    뱀부 개조는 부품값이 비슷하다(추정). **난이도로 갈린다**: REP5X 는 지침·BOM·
    펌웨어가 다 있고 역기구학과 배선 감김을 하드웨어가 해결한다. 뱀부 개조는
    기계 설계부터 전부 새로이고 **1ms 동기라는 성립 여부 문제**가 남아 있다
12. **REP5X 용 슬라이서 구현이 Open5x 보다 쉽다** — 좌표 변환을 **빼면** 된다.
    부품좌표 그대로에 `B=θ`(상수), `C=φ(p)`(방위각) 만 붙인다.

### REP5X 출력 모드 (`conical/rep5x.py`, `rep5x_check.py`)

```
python3 conical_slice.py model.stl --angle 20 --mode rep5x
python3 rep5x_check.py model_rep5x.gcode
```

펌웨어 설정(`Rep5x-Marlin`, `Marlin2ForPipetBot` 브랜치)에서 규약을 확정했다:
`PENTA_AXIS_HH`, `DEFAULT_TOOL_CENTERPOINT_CONTROL true`(RTCP 기본 ON →
**X/Y/Z 는 노즐 팁**), `AXIS4_NAME 'C'`(±360°), `AXIS5_NAME 'B'`(±135°),
LB=54.67mm, LC=1.6mm, `PRINTABLE_RADIUS 100`.

13. **공구 방향에서 각도가 유도된다** — `d̂ = Rz(C)·Ry(B)·(0,0,−1)` 을 원뿔 법선의
    반대와 맞추면 **B = c·θ (상수), C = φ(p)**. 부호가 틀리면 노즐이 반대로 기운 채
    출력이 시작되고 **G-code 만 봐서는 멀쩡해 보이므로**, 테스트가 (B,C)를 공구
    방향으로 되돌려 해석식과 대조한다
14. **⚠⚠ 정정: REP5X 도 되감기가 필요하다** — 앞서 "C축이 무제한이라 되감기 0"
    이라고 쓴 것은 **틀렸다.** "Continuous yaw rotation" 은 **슬립링이 푸는 기계적
    제약**이고, 펌웨어는 `I_MIN/MAX_POS = ±360` 에 소프트 엔드스톱이 켜져 있다.
    funnel 이 **44.7회전**, lamp 가 **220.7회전** 누적되므로 그대로 걸면 멈춘다
15. **제약의 종류가 달라 알고리즘도 다르다** — Open5x 는 '시작점 기준 이탈'(가까운
    쪽으로 되감기), REP5X 는 **절대 창**이다. 가운데로 되감으면 나머지 각도(±180°)
    때문에 한 바퀴만 더 감겨도 넘는다. `add_c_rewinds` 는 **다음 트래블까지 훑을
    범위를 미리 보고** 창에 맞는 k 를 고르고, 없으면 **못 고친다고 알린다**

16. **헤드 회전식에서도 간섭이 구조적으로 불가능하다 (outward 한정)** — 워프 함수
    `F = z + r·tanθ` 가 **볼록**이라, 공구 축 `∇F(p)` 에 대해 이미 놓인 모든 점이
    `∇F(p)·(q−p) ≤ F(q)−F(p) ≤ 0` 을 만족한다(지지초평면). 실측: funnel 50° 에서
    3축은 **40.22%** 간섭인데 헤드 회전식은 **0.00%** 다.
    검사기 B 를 **공구 프레임**으로 일반화해서 쟀고, 3축은 `u=(0,0,1)` 인 특수
    경우로 **결과가 비트 단위로 같다**(테스트가 강제) — 그래야 비교가 성립한다
17. **⚠ inward 원뿔은 두 5축 방식 다 안전하지 않다** — `F = z − r·tanθ` 는 **오목**
    이라 논증이 뒤집힌다. funnel 32° inward: 헤드 회전식 **61.28%** 간섭, 베드
    틸트식은 기계 Z 가 **7.4mm 내려간다.** 위 7번의 '평면 적층' 은 **outward
    한정 결론**이다. 우리가 쓰는 건 outward 지만, 문서에 명시해 뒀다

⚠ `--arm-radius` 를 주지 않으면 **B_arm 을 모델에 안 넣는다.** 저장소에 치수가
없어서다 — 모르는 값을 조용히 가정하면 '통과' 가 근거 없는 안심이 된다.
⚠ 축 부호는 조립에 달렸다. **첫 출력 전 `G0 B10` 을 눈으로 확인할 것.**

### 표면 품질·치수 정확도 (R5) — `analyze_quality.py`, `docs/experiment_plan.md`

⚠⚠ 표면 품질의 상당 부분은 **실물 없이는 못 잰다**(물리). 여기서 내는 것은
**기하가 강제하는 하한**이고, 실물이 나오면 이 예측이 **검증 대상**이 된다.

18. **계단 자국은 서포트 감소와 상충한다** — `cusp = d·|n̂·b̂|` 이라, 서포트를
    줄이려고 레이어를 표면과 나란히 놓으면 계단이 **최대**가 된다. lamp 에서
    서포트가 0 이 되는 θ=45~60° 에서 정렬이 평면 대비 **1.09~1.25배**, 면적의
    **44~70%** 가 평면보다 나빠진다. ⚠ 같은 층고로만 비교하면 `cosθ` 이득이
    전면적에 깔려 이게 **가려진다**. ⚠ 형상 의존 — funnel(얕은 접시)은 상충이 없다
19. **회전축 각분해능이 반경에 비례하는 치수 오차를 만든다** — REP5X C축
    26.666 steps/deg = 0.0375° → 반경 20mm 에서 **13µm**, 50mm 에서 **33µm**.
    R2 의 동기 오차(`f·Δt`)는 **반경 무관**이었다. 성질이 다르고 더해진다
20. **⚠⚠ R3 정정: 회전축 제원 가정이 틀린 쪽으로 틀렸다** — 실측 제원을 찾았다.
    최대 속도는 가정(360)보다 **10배 빠른데**(3600) **가속도는 3.6배 느리다**
    (1800 가정 → 실제 **500** deg/s²). R3 이 '가속도가 더 먹는다' 고 했으므로
    실제 기계는 **중요한 쪽에서 가정보다 나쁘다**
21. **R2 의 `ω = f/r` 이 가속도 제한으로 다시 나타난다** —
    `a_seg ≤ rot_acc · r / 57.3`. funnel 에서 `a_seg` 중앙이 **71 mm/s²**
    (XY 는 3000) — **축 근처가 가속도 굶주림**이다. C축 가속도를 500 → 20000 으로
    올리면 출력 시간이 **12.28 → 4.39분**. `M204` 가 REP5X 의 가장 큰 시간 레버다

실물이 나왔을 때의 실험 절차는 [`docs/experiment_plan.md`](docs/experiment_plan.md)
에 미리 짜 뒀다 — 판정 기준을 **보기 전에** 적어 두는 것이 요점이다.

### 검사기 C: Open5x 기계좌표 사전 점검 (5축)

```
python3 open5x_check.py out_open5x.gcode --bed-radius 90
```

검사기 A/B 는 **3축 가정**(노즐 수직, 베드 고정)이라 5축 출력에는 맞지 않는다.
검사기 C 는 기계좌표 자체를 본다 — 틸트 한계, **배선 감김**,
축 근처 **V 급회전**, 기계 Z 음수(소프트리밋), 베드 이탈, 피드 한계.

실제 출력(funnel, 20°)에서 셋이 걸린다. 고쳐야 할 버그가 아니라 **실기 전에
사람이 알아야 할 사실**이다:

| 걸린 것 | 값 | 뜻 |
|---|---|---|
| 배선 감김 | **44.5회전** | 슬립링이 없으면 배선이 끊어진다 → **되감기로 해결** (아래) |
| V 한 걸음 | **179°** | 축 근처 방위각 반전. 베드가 급회전하며 출력물을 흔든다 |
| 기계 Z 최소 | **−2.45mm** | 틸트로 베드가 내려간 쪽이라 음수가 정상일 수 있다. 펌웨어 소프트리밋이 0 이면 잘려서 노즐이 파고든다 — Z 오프셋 확인 |

감김은 **시작 기준 최대 이탈** `max|V − V₀|` 이다. Σ|ΔV|(총 회전량, 같은 파일에서
175회전)가 아니다 — 왕복은 배선을 감지 않는다. 총 회전량은 마모·시간의 척도로 따로 본다.

⚠ 축 가속도 한계와 실제 기구 충돌은 **보지 못한다.** 통과해도 첫 출력은 사람이
지켜봐야 한다.

### 배선 감김 대책: 트래블 중 V 되감기

```
python3 conical_slice.py model.stl --mode open5x            # 기본으로 켜져 있다
python3 conical_slice.py model.stl --mode open5x --v-rewind 0   # 끄기(슬립링이 있으면)
```

**되는 이유**: 베드를 정확히 360° 돌리면 부품은 제자리로 온다 — `Rz` 가 360°
주기라 **부품 점의 기계좌표가 변하지 않는다.** 그래서 되감기 이동은 X/Y/Z 를
건드리지 않고 V 만 바꾼다 (회귀 테스트가 툴패스 보존을 강제한다).

⚠ 다만 **도는 도중의 중간 각도**에서는 부품이 다른 방향을 향한다. 그래서 되감기
전에 **여태 퇴적한 것보다 위로** 들어올린다(기본 +2mm).

실측 트레이드오프 (funnel 20°, 회전 속도 1200 deg/min):

| `--v-rewind` | 되감기 | 감김 | 추가 시간 |
|---|---|---|---|
| 0 (끔) | — | 44.5회전 | — |
| 0.5 | 148회 | 1.0회전 | 44분 |
| **1.0** (기본) | 32회 | **2.0회전** | **15분** |
| 2.0 | 16회 | 3.0회전 | 13분 |

0.5 는 1.0 보다 시간이 3배 드는데 감김은 1회전밖에 못 줄인다. **진짜 한계는
기계의 배선 여유에서 와야 한다** — 서비스 루프를 재서 정할 것.
`--v-rewind-feed` 를 올리면 추가 시간이 비례해서 준다 (축 속도 한계 확인 후).

### 층고가 판정을 바꾼다 (2026-09-26) — `analyze_layer_height.py`

층고를 바꿀 때 **프로필은 다시 고르지 않는다.** 층간격 제약이 비율
(`m = 1 − c·r·s`)이라 층고에 무관하고, 실제로 0.3/0.4 에서 같은 `[30°,0°]` /
블렌드 2.31mm 가 나온다. 그래서 **원인이 층고 하나로 분리된다.**

진짜 오버행 %p (낙관 = 현재 기본 판정, 비관 = `require_supported_below=True`):

| 모델 | 낙관 판정 | 비관 판정 |
|---|---|---|
| 램프 (=허리 r=2), 0.2~0.5 6점 | 0.2mm 만 균일, 나머지 밴드2 | **경계 0.30~0.35** |
| 허리 r=3, 0.25~0.5 4점 | **전 구간 밴드2** | **경계 0.30~0.40** |
| 구, 0.25~0.5 4점 | 전부 무승부 | 전부 무승부 (균일로 수렴) |

1. **오버행은 층고에 단조 증가한다** — 양쪽 전략 다. 그래서 **층고를 안 적은 오버행
   수치는 비교가 안 된다.** 위 모든 표에 층고를 붙였다.
2. **낙관 판정은 층고에 대체로 둔감하다.** 뒤집힘은 램프 0.2mm 한 점이고 거기서
   균일 0.000 vs 밴드2 0.020 으로 **사실상 동률**이다. 허리 r=3 은 전 구간 일관.
   ⚠ 처음엔 이걸 "밴드 우세가 층고 조건부다" 라고 과장해 적었다 — 한 점이었다.
3. **비관 판정의 경계는 두 모델에서 재현된다** (0.30~0.35, 0.30~0.40).
   즉 **층고 ~0.3mm 이하면 비관 모델에서도 밴드가 이기고, 그 위면 진다.**
   → 실험 A 를 **0.4mm 로 뽑는 설계 근거가 유지된다**(두 지지 모델이 거기서 갈린다).
   그리고 **0.3mm 도 같이 뽑으면** 둘 다 밴드2 승이라 '두 모델 다 틀렸나' 를 따로
   판정할 수 있다 → [`docs/experiment_plan.md`](docs/experiment_plan.md)

⚠ 훑은 것은 0.2~0.5mm 6점(램프)·4점(대조 2종)이다. **그 밖은 모른다.**

#### 곁가지 — 검사기가 층고를 못 읽고 있었다

`toolpath_check.py` 의 `detect_layer_height` 가 `layer_h=` 패턴만 찾았는데
**우리 G-code 에 그런 문자열이 없다**(자기기술 헤더는 `;CONICAL_META` 의
`"layer_height"`). 그래서 **항상 폴백 0.3 을 쓰고 있었고** 0.3mm 파일에서만 우연히
맞았다. 램프 밴드2 가 0.89%p 로 보고되다가 고친 뒤 **0.77%p**(= `compare_waist` 와
일치)가 됐다. **자기기술 헤더를 넣는 것과 그것을 읽는 것은 다른 일이다**
(`tests/test_layer_height_detect.py` 가 고정, 못 읽으면 경고한다).

### ⚠⚠ 검사기의 공유 가정 — 위 계층이 답하지 못하는 것 (2026-09-23)

외부 리뷰가 "검증기가 슬라이서와 가정을 공유한다"고 지적했다. 위 ③층(브라우저
독립 재구현)·⑤층(팀메 독립 구현)은 **이 지적의 답이 되지 않는다** — 둘 다
**같은 판정 기준**을 다시 구현한 것이기 때문이다.

> **구현 독립 ≠ 가정 독립.** 우리가 가진 것은 앞쪽뿐이었다.

그래서 검사기의 가정을 직접 끊어 봤다 (`analyze_checker_assumptions.py`,
`check_support` 의 `vwin_factor` / `require_supported_below` / `bed_factor`).
셋 중 **하나가 진짜 결함**이었다.

**✅ 결함 — 베드 지지 규칙이 평면 층을 가정하고 있었다.** 규칙은
`supported |= z ≤ vwin` 이었다.
· **평면**이면 층이 z=상수라 이게 정확히 **1 층만** 잡는다(2 층은 2h). 그래서
  평면 대조군(원기둥·직육면체, `tests/test_known_answer_support.py`)은 통과한다.
· **원뿔**이면 한 층이 여러 z 에 걸쳐 **2 층 일부까지 끌어온다.** 실측(`허리 r=1`):
  베드로 찍힌 136 점 중 48 점이 그 구간에 있고 **48 점 전부 아래에 재료가 없다** —
  공중인데 통과된다. 그리고 그것들이 다시 위층의 지지 근거가 된다.
→ `bed_factor` 를 분리하고 **기본값을 1.0 으로 바꿨다**(첫 층만 베드).
  결과: 오버행 수치가 **중앙 1.21 배**(밴드2 는 최대 2.8 배) 올라가고,
  **승패 순위는 17/17 그대로**다. 평면(0°) 수치는 **안 움직인다.**
  옛 수치 재현은 `bed_factor=None`.

**❌ 결함 아님 — 지지 창 상수 `1.5` 가 `MAX_SPACING_FACTOR` 와 같은 것.**
   가장 의심스러워 보였고 외부 리뷰가 겨눴을 지점이지만, 창을 1.2~1.8 로 바꿔도
   **판정이 0/17 뒤집힌다**(= 하나도 안 바뀐다). 공유는 사실이나 결과를 만들지는
   않았다. ⚠ 뭉뚱그려 "설정에 따라 11/17 이 바뀐다" 고 세면 이 상수를 엉뚱하게
   범인으로 만든다 — **손잡이별로 갈라서 귀속해야 한다**(창 0/17, 연쇄 11/17).

**⚠⚠ 미해결(결함이 아니라 모델링 선택) — 미지지 재료가 지지로 세어진다.**
   `check_support` 는 이전에 퇴적된 **모든** 점을 후보로 쓰고 `supported` 로
   거르지 않는다. `require_supported_below=True` 로 끊으면 오버행이 **중앙
   +6.5%p**(최대 +29%p) 뛰고, 더 중요하게 **밴드 우세가 11/17 → 0/17 로 사라진다.**
   즉 **이 가정 위에서는 밴드가 한 번도 안 이긴다.**

   어느 쪽도 옳지 않다 — 현재값은 **낙관적 하한**(처진 비드도 온전한 지지로 침),
   연쇄는 **비관적 상한**(전혀 못 받친다고 봄)이다. 기본값은 안 바꿨다(결함이
   아니라 선택이므로). **이 폭은 실물 출력으로만 좁혀진다** —
   [`docs/experiment_plan.md`](docs/experiment_plan.md) 의 첫 실험에 이 축을 넣을 것.

   > **이것이 지금 이 연구에서 가장 큰 미확정 요인이다.** 위 모든 밴드 우세 주장은
   > "처진 비드도 위층을 받친다" 는 가정 위에 서 있다.

```

### 판정 기준 (통일됨)

오버행/서포트 판정은 **해석식**(`analytic.py`: 면이 실공간 국소 원뿔 레이어와
이루는 각, `g = n_z·cosθ + d·n_r·sinθ`)으로 통일했다. 변환공간 방식
(`sweep.py`/`metrics.py`)은 α>0에서 물리와 어긋나(비등각 왜곡,
`docs/warped_threshold_finding.md`) 레거시 비교용으로만 유지한다.

의존성 참고: `rtree`가 없으면 내장 슬라이서/레이어별 판정이 죽는다
(`requirements.txt`에 포함).

### 연구 논지: 균일 원뿔 vs 부위별 각도

비교 대상은 RotBot식 **균일 원뿔(모델 전체 각도 1개)**. 우리 방법은 모델을
**높이 구간으로 나눠 각 구간에 최적 각도**를 준다(= 변수각 원뿔 θ(z)). 균일각은 전체 타협값이라 손해고,
구간별은 '각도 예산'을 오버행 심한 구간에만 몰아써서 **더 적은 왜곡으로 오버행을
더 줄인다** — 단 허리가 있을 때만 (아래 표). `compare_complexity.py`가 균일/구간2/구간3/세밀을 **서포트·강도proxy·
평균각·계산시간**으로 비교한다(복잡도 vs 성능 가성비 곡선).

> **θ(z) 자체가 이 저장소의 확장이다** (2026-09-21, RotBot 원문 대조로 확정).
> 앞서 이 문단은 "RotBot 의 `var_angle` 방식"이라고 썼는데 **틀렸다.** RotBot 의
> `Scripts for Variable Angle` 에서 'variable' 은 **실행마다 고르는 상수각**이라는
> 뜻이다 — README 원문 *"the cone angle **can be changed** … not only 45° … but also
> much smaller angles (e.g. 15°)"*, 그리고 `Transformation_STL_var_angle.py:13` 의
> `CONE_ANGLE = 16` 은 스칼라다(`:35` `np.tan(cone_angle_rad)`, z 의존성 없음).
> 기본 스크립트는 45° 하드코딩(`Backtransformation_GCode.py:40` "divided by sqrt(2)").
> **따름**: 블렌드와 층간격 배율 `m` 은 RotBot 의 문제공간에 **존재하지 않는다** —
> 상수각이면 `s = dT/dZ′ = 0` 이라 `m ≡ 1` 이다. 이 제약은 θ 를 높이의 함수로
> 허용해야 비로소 생긴다. 차용한 것은 **변환식과 3단계 구조**이고(`transform.py`),
> **θ(z) 확장·그 제약의 유도·자동 선택**이 이 저장소의 몫이다.
> ⚠ 논문 본문(Appl. Sci. 11(18):8760)의 future work 절은 미확인(망 차단).

**단, 툴패스로 실측해 보니 조건부다** (`compare_waist.py`):

> ⚠ **'페리미터 미지지' 열은 오버행이 아닌 몫을 섞어 센다.** 위로 좁아지는 형상은
> 페리미터가 아랫층 단면 **안**에 놓이는데(희소 인필을 건너뛰는 평범한 브리징)
> 검사기가 그걸 미지지로 셌다. 섞인 비율이 행마다 0~67% 로 달라 **순위를 바꾼다.**
> 갈라낸 수치가 '진짜 오버행' 열이고, **결론은 이쪽으로만 읽는다.**
> → [`docs/verification.md`](docs/verification.md) 2026-09-19 절

> ⚠⚠ **이 표는 층고 0.4mm 기준이다** (`compare_waist.LAYER_H`). 층고를 안 적으면
> 의미가 없다 — 오버행은 층고에 **단조 증가**하고 폭이 크다(구: 낙관 판정 기준
> 0.25mm 0.018%p → 0.5mm 1.630%p, **90 배**). 2026-09-26 까지 이 저장소의 표 어디에도
> 층고가 안 적혀 있었다. → `analyze_layer_height.py`, 아래 '층고가 판정을 바꾼다'

| 모델 | 전략 | (페리미터 미지지) | **진짜 오버행** | 평균 왜곡각 |
|---|---|---|---|---|
| 구 (허리 없음) | 평면 0° | 7.51% | 4.90%p | 0° |
| | 균일 28° (J) | 1.31% | **0.75%p** | 28° |

| | 균일 24° (J) | 3.21% | 1.21%p | 24° |
| | **밴드2 (J)** | 1.27% | **0.77%p** | **18.6°** |

> **⚠ 2026-09-23: 이 표의 원뿔 행이 전부 올라갔다** (구 0.51→0.75, 램프 1.01→1.21,
> 밴드2 0.33→0.77). 검사기의 **베드 지지 규칙이 평면 층을 가정**하고 있어서
> 비평면 출력에서 공중에 뜬 점을 '베드에 붙었다' 고 통과시키고 있었다
> (`bed_factor`, 아래 '검사기의 공유 가정' 절). 그만큼 **낙관적이었다.**
> **평면(0°) 행은 안 움직였다** — 평면 층에서는 그 규칙이 원래 맞기 때문이고,
> 결함이 비평면에서만 나타난다는 진단이 여기서 한 번 더 확인된다.

읽는 법 둘.

**① 원뿔이 평면을 이긴다.** 구 4.90 → 0.75%p (**6.5배**), 램프 2.71 → 1.21%p (2.2배).

**② 허리가 있으면 밴드가 균일각을 두 축에서 지배한다.** 램프에서 오버행 1.21 →
**0.77%p** (**1.57배**)이면서 왜곡도 24.0° → **18.6°** 로 줄었다. 파레토 우세다.
허리가 없는 구에서는 밴드가 스스로 균일로 수렴한다 — 블렌드가 비싸서다.
⚠ 베드 규칙을 고치기 전에는 이 배수를 3.1 배로 적고 있었다. **1.57 배가 맞는 수다.**

> ⚠ **열린 질문**: 구에서 선택에 블렌드 비용을 아예 안 넣은 해(`select_banded`)가
> 0.63%p / 18.9° 로 균일(0.75%p / 28.0°)을 두 축 모두에서 약간 이긴다. "구에서는
> 균일이 정답"이라는 전제 자체를 다시 봐야 한다. 지금 J 는 그 해를 못 고른다.
> (베드 규칙 수정 뒤에도 이 관계는 유지된다.)

각도를 바꾸려면 블렌드가 필요하고 그 폭은 **그 높이의 반경에 비례**한다
(층간격 제약). 그래서 각도 변경은 '가는 곳에서 싸고 뚱뚱한 곳에서 비싸다' —
구처럼 어디나 뚱뚱하면 블렌드가 모델 높이의 73%를 잡아먹어 균일각이 낫다.
이 조건은 우리가 가정한 게 아니라 검사기가 실측으로 알려준 것이다.

그래서 밴드 선택을 **프로필 단위 J** 로 바꿨다(`select_banded_j`): 후보 각도로
실제 프로필을 만들어(층간격 제약 포함) J 를 재고, 여기에 해석식이 못 보는
블렌드 비용을 명시적으로 더한다.

```
J = (서포트 감소 %p) − k×평균|θ| − k_blend × Σ(블렌드 구간 표면적 %)×(m−1)/(limit−1)
```

탐색 이웃은 '연속한 밴드 덩어리'다 — 블렌드 비용이 '이웃 밴드의 각도가 다른
자리'에 붙으므로 한 칸씩 바꾸는 이웃으로는 두 밴드를 함께 내리는 수를 못 둔다.
균일 후보를 전수 평가해 섞으므로 **결과가 최선 균일 원뿔보다 나쁠 수 없다**
(회귀 테스트로 강제).

**`k_blend` 기본값은 0.5 → 0.1 로 낮췄다** (2026-09-19). 0.5 는
`analyze_blend_k.py` 가 낸 창(0.1~1.5)의 한가운데였는데, 그 창의 '정답'
("구=균일, 램프=부위별")이 **오염된 지표**로 정의돼 있었다. 진짜 오버행으로
다시 재니 0.5 는 과하다 — 램프 밴드2 에서 `k_blend=0.5` 는 1.12%p/16.3°,
`0.1` 은 **0.33%p**/18.6° 로 3.4배 낫고, 구에서는 둘이 같다(균일로 수렴).
0 으로 두면 여전히 병리적이다(구에서 `[36°, −44°]`, 블렌드 19.9mm, 1.81%p).

밴드 수를 늘렸을 때의 곡선은 `compare_bands.py` 가 그린다 (진짜 오버행 %p /
평균 왜곡각). 표본 7개 × N=1~6 으로 재측정한 결과:

**밴드 수 N 을 늘릴 이유가 없다.** 다만 이유는 "J 가 포화해서"가 **아니다** —
`k_blend=0.1` 에서 J 는 N=6 까지 계속 오른다. 그런데 **진짜 오버행은 거기서
나빠진다**: 7개 중 6개에서 J 최대 N 의 오버행이 달성 가능한 최소보다 나쁘다
(구 N=5 → 1.84%p vs 최소 0.51%p, 허리 r=3 N=6 → 1.39%p vs 최소 0.32%p).

결함이 아니라 구조다. J 는 경계가 겹치는 짝에서 N 에 대해 비감소이므로 N 을 J 로
고르면 항상 커지는 쪽으로 가고, 각도 비용 k 때문에 '밴드 많고 각도 낮은' 해를
선호한다. **그래서 N 은 사람이 준다**(`--auto-bands N`, 기본 2). 자동화하려면
N 자체에 대한 비용이 따로 필요하다.

**J 가 N 에 대해 비감소인지**가 이 실험의 자체 점검이다. 처음엔 위반했고, 그걸
따라가 계획기 결함 셋을 찾았다 (docs/verification.md). 다만 그 점검의 원래 논거
("N개는 이웃을 같은 각도로 두면 N−1개를 흉내낼 수 있다")는 **틀렸다**: 밴드 경계가
`linspace` 라 N=3 의 경계(33.3%, 66.7%)는 N=4 의 경계(25/50/75%)에 하나도 없다.
흉내내기가 보장되는 짝은 **n 이 m 을 나눌 때뿐**이고(1→2, 2→4, 3→6 …), 그 짝에서만
감소가 결함이다. 이웃한 N 사이의 감소는 격자 비정합이다
(`tests/test_band_nesting.py` 가 고정).

모델 표본은 `--waist-sweep` 으로 늘린다. 목 반경을 7→1 로 바꾸면 허리 두드러짐
(`conical.meshio.waist_prominence`) 이 0.00→0.86 으로 움직인다. 밴드2 기준 오버행
감소 배수(목 반경 축, r=4 는 2026-09-21 추가):

| 허리 두드러짐 | 0.00 | 0.00 | 0.29 | **0.43** | 0.57 | 0.71 | 0.86 |
|---|---|---|---|---|---|---|---|
| 오버행 감소 | ×1.0 | ×0.9 | ×0.9 | **×1.3** | **×1.7** | **×1.6** | **×1.8** |

이 축에서만 보면 문턱이 0.29 와 0.43 사이로 보인다.
⚠ 베드 규칙을 고치기 전에는 이 배수를 ×1.4 / ×3.3 / ×3.1 / ×4.1 로 적고 있었다
(2026-09-23 재측정). **문턱 위치는 그대로이고 이득의 크기만 줄었다** — 3~4 배가
아니라 **1.6~1.8 배**다.

> ### ⚠⚠ 그런데 허리 두드러짐은 **판정 기준이 아니다** (2026-09-21, 반증됨)
>
> 위 표는 **목 반경 하나만** 움직인다. 허리 깊이를 **그대로 둔 채** 모델을 XY 로만
> λ 배 하면(`analyze_blend_ratio.widen`) 두드러짐은 비율이라 **0.571 로 고정**인데
> 블렌드 폭은 `w = r_b·|Δtanθ|/(limit−1)` 로 `r_b ∝ λ` 만큼 비싸진다. 실측하면
> **같은 0.571 에서 승패가 갈린다**:
>
> | 허리3 ×λ | ×1 | ×1.1 | ×1.2 | ×1.3 | ×1.5 | ×2 |
> |---|---|---|---|---|---|---|
> | 두드러짐 | 0.571 | 0.571 | 0.571 | 0.571 | 0.571 | 0.571 |
> | 판정 | **승** | **승** | **승** | **패** | **패** | **패** |
>
> 두드러짐 0.571 이 **승 3건·패 3건 양쪽에 나온다** → 이 지표로는 못 가른다.
> 지표 자체는 멀쩡하다(형상을 재는 데는 맞다). **기준으로 쓴 것이 틀렸다.**
>
> **대신 쓰는 것**: 블렌드 비용과 잠재 이득이 같은 단위(표면적 %)라는 점을 쓴다.
>
> ```
> ΔS_ideal = (균일 최적 서포트) − (블렌드를 무시한 밴드 최적 서포트)   ← 이득
> cost     = varangle.blend_penalty(그 이상적 밴드로 만든 실제 프로필)  ← 비용
> ρ        = cost / ΔS_ideal                                        ← 무차원
> ```
>

> 선택기가 밴드를 고르는 조건 `ΔS + k·Δθ̄ > k_blend·cost` 를 ρ 로 풀면
> `ρ < (1 + k·Δθ̄/ΔS)/k_blend` 이므로 문턱이 `1/k_blend` 에 비례해야 하고, 실측이
> 그렇다 — `k_blend` 를 2 배 올리니 ρ* 가 2.42 배 내려갔고 곱 `ρ*·k_blend` 는

## 튜닝

바꿀 값은 전부 `conical/config.py` 한 곳에 있다.
- `THRESHOLD_DEG` : 오버행 판정 임계각 (기본 45°)
- `MAX_ANGLE_DEG` : 하드웨어가 허용하는 최대 원뿔 각도 (하드코딩 금지, 여기서 조정)
- `ANGLE_STEP`   : 각도 탐색 간격
- `MAX_SPACING_FACTOR` : 블렌드 층간격 배율 상한 (기본 1.5)
- `BLEND_SHIFT_RATIO`  : 밴드 경계를 '허리'로 옮겨보는 최대 거리 (모델 높이 × 이 값, 기본 0.25)
- `BLEND_COST_K`       : J의 블렌드 비용 가중치 (기본 0.5, 창 0.1~1.5)
