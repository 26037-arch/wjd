## 1. 수식은 완전히 같다

두 저장소가 독립적으로 작성됐는데 판정식이 문자 그대로 같다.

| | 우리 `conical/analytic.py` | 팀메 `conical_slicing/evaluation.py` |
|---|---|---|
| 점수 | `g = n_z·cosα + d·n_r·sinα` | `_score()` — 동일 |
| 임계각 | `α* = asin(κ/R) − atan2(n_z, d·n_r)` | `minimum_feasible_angle()` — 동일 |
| 구현 | numpy 벡터화, 도달 불가 시 NaN | 면 단위, 주기 사인 구간 교차 + 실패 시 대체각 |

`compare_with_teammate.py` 가 **같은 κ 를 넣고** 면별 임계각을 대조한다.

```
3모델(구·램프·funnel) × 2방향, 약 22,000면
  g(α) 최대 차이   : 0.00e+00
  임계각 최대 차이 : 1.42e-14°  (부동소수 잡음)
  도달 불가 면 집합: 정확히 일치 (192/192, 1984/1984, 32/32)
```

**이것이 실물 출력을 대신하는 검증 층이다.** 물리 실험이 불가능한 조건에서
"우리 계산이 맞다"의 마지막 근거는, 같은 수식을 다른 사람이 따로 구현한 코드와
맞아떨어진다는 사실이다. 남는 것은 두 사람이 같은 실수를 했을 확률뿐이다.

## 2. 진짜 차이는 κ 를 무엇으로 두느냐였다

이게 두 코드의 수치가 어긋나 보였던 근본 원인이다.

| | 규칙 | 범위 |
|---|---|---|
| 우리 | 고정 `κ = −sin(45°) ≈ −0.7071` | 항상 45° |
| 팀메 | `q = B/√A`, `κ_c = −κ_max·q/(q+q₀)` (κ_max=0.3, q₀=1) | κ ∈ (−0.3, 0] → **0°~17.5°** |

팀메 규칙의 발상은 좋다 — **둘레가 길고 면적이 작은 오버행 성분일수록 관대하게**
본다(가늘고 긴 오버행은 브리징으로 걸쳐진다). 우리 규칙은 형상을 전혀 안 보는
대신 실제 슬라이서 관례(Cura의 45°)에 앵커돼 있다.

### 실측 판정 (`compare_kappa_rules.py`)

각도 6개에 대해 두 규칙의 예측을 툴패스 실측(페리미터 미지지 %)과 대조:

| 각도 | 구 실측 | ①고정 예측 | ②형상 예측(κ_max=0.3) |
|---|---|---|---|
| 0° | 7.51% | 14.88% | 14.88% |
| 8° | 2.30% | 10.58% | 14.88% |
| 16° | 1.53% | 6.62% | 14.88% |
| 24° | 1.27% | 3.66% | 14.88% |
| 32° | 0.95% | 1.24% | 14.22% |
| 40° | 1.04% | 0.29% | 9.39% |

순위상관: **①고정 ρ=+0.943 / ②형상 ρ=+0.778** (램프에서는 +0.943 / +0.655).

원인이 표에 보인다 — ② 는 0~24°에서 예측이 **14.88% 로 상수**다. 임계가 너무
엄격해서 각도를 올려도 판정이 안 바뀐다(포화). 각도를 못 매기니 순위가 어긋난다.

### 그런데 아이디어가 아니라 눈금의 문제였다

`κ_max` 를 올려 유효 임계각을 45° 근처로 맞추면 결과가 달라진다:

| κ_max | 구: 유효 임계각 / ρ | 램프: 유효 임계각 / ρ |
|---|---|---|
| 0.300 | 14.2° / +0.778 | 13.3° / +0.655 |
| 0.500 | 24.1° / +0.880 | 22.5° / +0.820 |
| 0.707 | 35.3° / +0.928 | 32.8° / +0.928 |
| **0.850** | **44.0° / +0.943** | **40.6° / +0.943** |
| 1.000 | 54.7° / **+0.986** | 50.0° / +0.943 |

**κ_max ≈ 0.85 에서 두 규칙이 만난다** (유효 임계각 44°, ρ 동일). 1.0 에서는
형상 의존 쪽이 오히려 조금 낫다. 즉 두 규칙은 대립이 아니라 **같은 눈금 위의
같은 지점**이고, 형상 의존은 그 위에 얹는 보정으로 보는 것이 맞다.

→ 통합 결론: 기본은 고정 45°(외부 관례 앵커)를 유지하되, 형상 의존 규칙을
`conical/kappa.py` 에 함께 두고 `κ_max` 의 근거를 위 표로 남긴다.
팀메 기본값 0.3 은 실측상 너무 엄격하다.

## 3. 부호 규약 — 어긋났고, 맞췄다 (viewer)

`conical-slice-viewer` 는 교선을 `q = z − r·tan(α)` 로 잡는데 우리 정변환은
`Z′ = z + c·r·tanθ` (c=+1 outward)다. 따라서 **뷰어의 α 양수 = 우리 inward** 였다.
같은 모델에 같은 숫자를 넣어도 두 도구가 **반대 원뿔을 그린다.** 뷰어의 기본값이
`angleDeg: -30` 이었던 것이 그 증거다 — 우리 기준으로는 outward 30° 다.
(`find_conical_angle` 의 `DIRECTION_SIGNS` 는 outward=+1 로 우리와 같다 —
어긋난 것은 뷰어 하나였다.)

**수정 방침**: 뷰어 내부 수식은 건드리지 않았다. 미분(`derivativeAtT`)·볼록성
가정·극값 탐색 방향(`findMinimum = tanAngle < 0`)이 전부 `q = z − r·tan` 을 전제로
짜여 있어서, `coneQ` 만 뒤집으면 나머지가 조용히 깨진다. 대신 **각도→탄젠트 변환
지점 두 곳**에서만 부호를 뒤집는다.

```js
// conicalMath.js — 변환은 여기 한 곳에서만 정의
export function tanFromStandardAngleDeg(angleDeg) {
  return -Math.tan((angleDeg * Math.PI) / 180);
}
```

호출 지점은 `slicingWorker.js`(슬라이싱)와 `ConicalViewer.js`(비드 렌더) 둘뿐이다.
UI 기본값 `-30 → 30`, 라벨에 `+outward / −inward` 명시, README 에 규약 문단 추가.

**검증**: 뷰어의 `coneQ` 와 우리 `transform_cone`(Python)을 10개 각도·방향 조합
× 5점에서 대조 → **차이 0.00e+0**.

⚠ 이 저장소는 팀메 소유라 직접 푸시하지 않았다. 패치 파일로 전달한다
(`git am` 또는 `git apply` 로 적용, 원본 최신 커밋에 깨끗하게 붙는 것 확인함).
`generateRasterInfill` 의 `angleRadians` 는 인필 래스터의 XY 회전각이라 원뿔각과
무관하다 — 손대지 않았다.

## 4. 서로 없는 것

| 팀메에 있고 우리에 없는 것 | 우리에 있고 팀메에 없는 것 |
|---|---|
| 성분별 지지 경계(bed/surface) 구분과 non-manifold 변 우선순위 | STL → 실제 G-code 파이프라인 (정변환·슬라이싱·역변환) |
| 형상 의존 κ | 가변각 프로필 θ(Z′)과 층간격 제약 |
| 연속 위반량 손실 `L = Σ A·max(0, κ−g)/A` | 툴패스 가상 검사기(지지·노즐 간섭) |
| 교선 시각화 (Three.js, Web Worker) | 브라우저 독립 재구현 대조·손계산 검산 |
| TOPPRA·FCL 연동 구조 검토 | 압출 종류 분리(`;TYPE:`) |

우리 `conical/clusters.py`·`bandplan.py` 는 이미 팀메 BFS 성분/밴드 정의를
미러한 것이고, 이번에 `conical/kappa.py` 로 κ 규칙까지 가져왔다.
