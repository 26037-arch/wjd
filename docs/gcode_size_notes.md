# G-code 100만 줄 문제 진단 (원뿔 변환 파이프라인)

팀메가 Slic3r로 변환 파이프라인을 돌렸더니 G-code가 ~100만 줄이 나오고 출력이
너무 오래 걸리는 문제. 원인 분석과 구체적 해법.

## 결론 먼저

1. **100만 줄 자체는 버그가 아니라 원뿔 파이프라인의 예상된 특성**이다.
   다만 **세그먼트가 필요 이상으로 잘게** 나뉘어 있을 가능성이 크고, 그게
   실제 속도 저하(버벅임)의 원인이다.
2. **줄 수 ≠ 출력 시간.** 출력 시간은 경로 길이·속도가 정하지만, 세그먼트가
   너무 짧으면 펌웨어가 초당 처리 가능한 세그먼트 수(8bit 보드 ~200/s,
   32bit ~1000-2000/s)를 못 따라가 **버벅이며(stutter) 실제로 느려진다.**
   → 진짜 문제는 "줄 수"가 아니라 "너무 짧은 세그먼트의 비율"이다.
3. 진단 도구: `python tools/gcode_stats.py print.gcode` 로 세그먼트 길이
   분포·버벅임 위험·감축 가능 배수를 바로 잴 수 있다.

## 왜 줄 수가 폭발하나 (3중 원인)

```
[원인1] 변환된 STL은 삼각형이 잘게 세분(refine)되어 있음
        → Slic3r 윤곽의 꼭짓점 수 자체가 많음
[원인2] Slic3r 해상도 설정(resolution, gcode resolution)이 기본값(매우 정밀)
        → 윤곽 단순화 없이 꼭짓점 전부 G1으로
[원인3] 역변환: 변환공간의 '직선' = 실공간의 '곡선'
        → 역변환 스크립트가 모든 G1을 짧은 세그먼트로 재분할 (보통 고정 간격)
        → 이게 주범. 고정 간격이 0.1mm면 곡률이 필요 없는 곳까지 잘게 쪼갬
```

## 해법 (효과 큰 순서)

### 1) 역변환 재분할을 '고정 간격'에서 '곡률 적응'으로
실공간에서 원뿔 경로는 축 중심의 원호에 가깝다. 반경 r인 호를 현(chord)으로
근사할 때 허용 오차 ε에서 **최대 현 길이 L = 2·√(2rε)** 이다.

| 반경 r | ε=0.05mm 허용 현 길이 | 0.1mm 고정 대비 |
|---|---|---|
| 5 mm  | 1.4 mm | 14배 |
| 30 mm | 3.5 mm | 35배 |
| 80 mm | 5.7 mm | 57배 |

→ RotBot Transform의 역변환 스크립트에서 재분할 간격을 이 식으로 바꾸면
   (축에서 먼 곳일수록 길게) **품질 손실 ε=0.05mm 이내로 수십 배 감축**이
   가능하다. 우리 `tools/gcode_stats.py`가 파일별 감축 가능 배수를 추정해준다.

### 2) Slic3r 설정
- `resolution` (Print Settings → Advanced): 0(무제한) → **0.0125~0.05mm**
- G-code resolution(있는 버전): **0.0125~0.05mm**
- 변환 전 STL의 refine 단계 밀도도 필요 이상이면 낮추기.

### 3) 호 명령(G2/G3) 압축 — ArcWelder
원뿔 경로는 축 중심 원호라서 호 피팅이 특히 잘 먹힌다. 역변환 후
ArcWelder(포스트프로세서)로 G1 연쇄 → G2/G3 변환하면 추가로 수 배 감축.
단, **펌웨어가 G2/G3를 지원해야** 함(Marlin `ARC_SUPPORT`, Klipper `gcode_arcs`).

### 4) 펌웨어 쪽 확인
- 보드가 8bit(예: Ender 스톡)면 초당 처리율이 낮아 짧은 세그먼트에 특히 취약.
- USB 스트리밍 출력이면 SD 카드 출력으로(통신 병목 제거).

## 진단 순서 (팀메 추천 절차)

```bash
# 1. 현재 파일 진단: 얼마나 잘게 쪼개져 있고, 몇 배 줄일 수 있나
python tools/gcode_stats.py print.gcode --chord-tol 0.05

# 2. p50 세그먼트가 0.1~0.2mm 수준이고 '감소 가능 배수'가 크면
#    → 역변환 재분할 간격을 곡률 적응(위 식)으로 수정
# 3. 그래도 크면 Slic3r resolution + ArcWelder 적용
```
